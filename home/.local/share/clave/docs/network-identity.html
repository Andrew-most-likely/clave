Network Identity

System Settings > Privacy & Security > Network Identity. Requirement SEC-7 and FEAT-10 in docs/PROJECT_PLAN.md.

Every device on a shared network (campus, café, hotel) can see a few things about this computer before any VPN starts: the DHCP request it sends to get an address, the time-to-live (TTL) of its packets, how it opens TCP connections, and whether it answers ping. Together these say "Linux". Network Identity changes them so the computer looks like another common device, or, with Stealth, answers as little as possible.

Look like

Choosing a profile runs pkexec /usr/local/bin/clave-netid apply PROFILE STEALTH. It asks for your password (polkit action org.clave.netid, then 5 minutes without asking again), writes the files below, loads the firewall rules and reconnects Wi-Fi and wired connections once, so the next DHCP request carries the new identity. Off runs clave-netid reset.

In every profile: a new random MAC address for each connection, the DHCP client id is that MAC (never a stable DUID), NetworkManager uses dhcpcd, and DHCP leases are forgotten on connect and disconnect, so two connections cannot be linked by a requested old address.

Why these values: they come from the p0f TCP fingerprint database, the satori DHCP fingerprint database and captures of real devices. Option 108 asks for "IPv6-only preferred"; it is sent in the request list but dhcpcd is told to ignore it, because IPv6 is off on the local network.

Stealth

Works with any profile (with Off it uses the Linux profile). It adds, on top of the profile:

  • Nothing new from the network gets an answer: ping, timestamp requests, connection attempts and mDNS are dropped without a reply. Only DHCP replies and error messages for this computer's own connections pass (nftables chain netid_in).
  • ARP is answered only for this computer's own address on the interface that asked (arp_ignore=1, arp_announce=2).
  • No DHCP hostname is sent.

Side effect: printers and other devices that find this computer through mDNS stop seeing it. Connections this computer opens itself work as usual.

Status

The row under the switches says when a part of the profile cannot be applied on this computer:

DHCP order and TTL

dhcpcd sends DHCP through a raw packet socket, which bypasses the firewall, so the TTL of DHCP packets and the order of option 55 can only come from dhcpcd itself. Stock dhcpcd always uses TTL 64 and sorts option 55 by number. An optional dhcpcd build reads both from /etc/clave/netid/dhcp; without it the options are right but their order and the DHCP TTL are not. Build instructions: scripts/extra/dhcpcd-netid/README.md in the Clave repo. clave-netid status shows dhcp_patch=yes when the build is installed.

TCP option order

Linux sends its own SYN option order whatever the TTL. clave-synshape reads the computer's own outgoing IPv4 SYNs from netfilter queue 7071 and reorders their options. It never adds an option and never changes a value (MSS, window scale, timestamps), so the connection is what the kernel set up. Before it is switched on, clave-netid runs a connection between two scratch network namespaces through it; if the kernel drops the rewritten packet, the rewriter stays off and the order stays Linux's (rewriter=failed). The rule uses bypass: if the service stops, SYNs go out unchanged. Profiles that use the kernel order (Android, Linux) start no service.

What it cannot change

  • The access point always sees a device that transmits. Network Identity changes what the device looks like, not whether it is there.
  • Wi-Fi probe and association frames are built by the iwlwifi driver and the kernel's 802.11 stack and look like Linux on an Intel card in every profile. The radio's own signal characteristics cannot be changed in software. Windows is the most believable profile, because Intel Wi-Fi cards are common in Windows laptops.
  • Traffic inside a VPN tunnel is not affected; the profile matters for what leaves outside it (DHCP, ARP, the captive portal login, ping replies).
  • A website can still tell what browser and system you use from the browser itself. The profile's user agent is only written to /etc/clave/netid/portal, for a captive portal login script to use; Clave does not change your normal browser.

Check it

What is set now, without root:

clave-netid status

What leaves the computer: start this, then reconnect Wi-Fi from the menu bar. DHCP shows its TTL, option 55 and option 60; a SYN shows up only for traffic outside the VPN, such as the captive portal.

sudo tshark -i wlo1 -c 6 -f 'udp port 67 or tcp[tcpflags] & tcp-syn != 0' \
  -T fields -e ip.ttl -e dhcp.option.request_list_item -e dhcp.option.vendor_class_id -e tcp.options

From a second device on the same network: ping this computer (Windows and Stealth: no reply), or nmap -O -Pn ADDRESS for an OS guess. Run the rewriter self-test again with sudo clave-netid selftest.

Turn it off

Choose Off in Settings, or from a terminal:

sudo clave-netid reset

It restores /etc/dhcpcd.conf, removes every file listed above, empties the firewall chains, stops the rewriter and restarts NetworkManager. If only the rewriter is suspect: sudo systemctl stop clave-synshape (connections go out unchanged). More in docs/RECOVERY.md.
